An end-to-end map of the KDM Tracker product: external statistics and Discord events, the Windows Mini PC, shared tracker state, durable refreshes, public releases, the website, AI responses, retained archives, emergency workflows, and traffic analytics.

Updated 22 September 2026. Start with the system map below, then follow a chapter to trace a specific input, calculation, or output. Production observations record the deployed state at a stated time.

KDM BF6 Tracker collects clan statistics, publishes rankings, and answers statistics questions through the KDM Tracker Discord bot. Cloudflare R2 stores files and archives; Cloudflare D1 stores website-traffic summaries. A release is a fixed set of generated files that the website reads together. A refresh collects new observations and publishes a new release.

The GameTools tuple comprises persona/player ID, nucleus/account ID, identity platform, and available platform metadata. Preferred launch platform and reviewed Tracker.gg mappings are separate metadata, not replacements for that identity tuple. Only the verified identity enters batch statistics requests. A same-account relink can retain the reviewed Tracker mapping; a different or unverifiable nucleus clears it, and an account change must not inherit the previous account's cached numbers.

Unlisting removes inactive-player noise from current public projections, not from collection or private retention. Relisting can restore the retained series without recollecting the unlisted period. Ordinary names and audit history are not treated as private by this filter. Earlier immutable public releases may still contain a member who was listed when they were published.

Unlink and permanent removal delete the registry entry and stop ordinary future collection. They do not erase previously retained archive observations. Removed identities receive stricter alias/profile-URL screening in public output. Unlist/relist immediately update the registry, post a confirmation, invalidate AI caches, and enqueue one single-flight cached site publication; changes arriving mid-publication cause a trailing rerun. A second AI invalidation follows publication. Discord standings follow on the next full refresh. Normal unlink/removal publication is deferred to that refresh; these paths must not be described as an atomic change across every surface.

Batch entries contain verified player ID, account ID, and exact identity platform. The documented defaults are ten members per chunk and two chunks in flight. format_values=true avoids the upstream behavior encountered with unformatted batch responses; normalization restores valid numeric values. A hard batch-stage deadline bounds requests and retries. Fast retryable failures may retry within that budget; timeouts do not. Failed, missing, invalid, or unresolved members fall back individually while other collection work continues. Profile rank is a separate request and does not invalidate otherwise usable statistics.

A cached field is not a new observation. Fresh fields replace previous fields, missing fields retain their last known presentation values, and entirely failed members can still appear with stale flags. The numeric archive merges the newest successful same-day payload per member and preserves earlier successful same-day observations when a later fetch fails. A run with no fresh payloads does not create an archive observation. Raw writing is best effort and separately monitored; a successful public refresh is not proof that raw capture or its offsite mirror succeeded.

Creation uses If-None-Match: *. Reusing a key with identical bytes is an idempotent retry; different bytes are a collision, not permission to overwrite. Pointer compare-and-set arbitrates concurrent publishers. A rendered release is checked against the listed-member set so a partially filtered release is not silently accepted. Publication retains the exact staged bytes for retries.

The active release plus thirty superseded releases are retained by count. An unreadable or inconsistent pointer stops deletion; releases newer than the pointer snapshot are protected from a concurrent retention pass. This is not an age-only bucket lifecycle policy and not permanent history storage. Public verification failure can leave an already advanced pointer requiring investigation; it does not mean the pointer was automatically rolled back.

Numerical boundaries

BF6_STAT_CONFIG owns ordered stat definitions. Player KPM uses exact human-player kills divided by active class-All minutes, not the upstream broader kills-per-minute value. Score/min and time played use the same active-time basis. Player K/D is distinct from bot-inclusive K/D. Weapon-only headshot percentage is distinct from all-kill counts. An unavailable rank of zero is treated as missing, not a real leaderboard fall.

Period performance uses differences of cumulative counters: for example, delta human kills divided by delta deaths. It is not the change in lifetime K/D and not an average of daily ratios. Missing observations, carried endpoints, tracking-start limits, zero denominators, and resets require explicit handling. Rate ranking qualification on the website is 15 active minutes per calendar day of the resolved window; count stats have no such threshold. Player Rank remains a Career-only progression stat.

Tracker days begin at midnight in America/Los_Angeles. Names such as easternDateKey and the legacy counters timezone metadata do not override that behavior; do not hard-code a fixed 3 AM Eastern rollover. current.settled and the artifact's date axis determine Today-so-far, not a browser's wall clock.

A counter formula-version bump alone need not disable every Period view. Consumers feature-detect required keys per stat. Renaming a key requires matching consumers; changing its meaning while keeping its name is more dangerous because structural checks cannot detect semantic drift. Effectiveness formula changes require the producer's model-version/fingerprint rebuild path. See the change register.

Eligibility requires an explicit bot tag in a configured BF6 channel, or a direct reply to a successfully generated AI message or an overtake message carrying its distinct invisible marker. An ordinary bot status message does not qualify. Bot/webhook conversation is ignored, existing BF6 commands have priority, and unrelated untagged discussion causes no model call. Referenced messages and earlier reply-chain text are bounded, untrusted conversation—not authority for new BF6 numbers or permission to execute instructions.

The compiler receives the current question, bounded context, identities/names, and a catalogue of approved subjects, metrics, items, categories, and operations. It does not receive the authoritative BF6 numerical dataset. The host validates the resulting plan, loads only appropriate local data, resolves windows and subjects, performs calculations, and constructs an ExecutionResult. Full-cohort operations evaluate the eligible roster before output slicing; explicit requested subjects must not disappear through silent truncation.

The writer receives the validated plan and execution result. It has no tools and is instructed not to invent or recompute BF6 numbers. This is a contract enforced by deterministic input construction and writer instructions; it is not a claim that every sentence of model output undergoes a mathematical proof check. Partial coverage and unavailable rows must remain visible in the answer.

Normal successful interaction uses two logical model calls. Transport-level behavior is distinct from that architectural count. Ordinary chat also follows compiler → empty successful host result → writer, but does not invoke the numeric query reader. Compiler/schema/validation failure may stop after the first call with a canned rephrase response. An incomplete writer response is not automatically regenerated through a third semantic stage.

The mirror script maintains bare bot, rankings, and archive repositories under C:\Bots\backups, including branches/tags/refs. Those mirrors help with repository/history loss, but sit on the same disk as production. They do not protect against loss of that disk, do not include ignored runtime data, and do not copy .env or credentials.

Offsite recovery is limited to what actually reached GitHub/R2 (and separately managed services such as D1). An unuploaded raw day, raw backlog, AI logs, local recovery outbox, or unique reconstruction evidence can still be lost. An instruction in a runbook to include ProgramData in a machine backup is not evidence that a backup job currently exists or that a restore was tested.
